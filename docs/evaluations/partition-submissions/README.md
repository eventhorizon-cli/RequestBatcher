# Submission APIs and partition count

Historical single-machine evaluation measured partition counts 1 and 4 at batch size 64 and concurrency 4, using production source `9be066a`, BufferQueue 2.1.0, .NET 10.0.0, and BenchmarkDotNet 0.15.8 on an Apple M2 Max (2026-10-26). It contains two independent experiments: concurrent `ExecuteAsync(request)` calls and explicit `ExecuteAsync(requests)` groups. Each API has its own one-partition control; results must not be compared across APIs. Both experiments validated response values and exactly-once handling, including explicit response order.

Across both APIs, four partitions fragmented SmallBurst workloads, reducing item throughput and increasing allocation. Backlog measurements showed overlapping timing uncertainty and no established benefit. RepeatedKeys improved throughput under the specific deduplication delay model: partition-local batches queried fewer distinct items, while allocation rose slightly in the explicit case. This model simulates downstream cost and does not represent a measured service. The charted means have uncertainty; detailed raw records are no longer retained. The [single-submission chart](../../assets/partition-submission-single.svg) and [explicit-submission chart](../../assets/partition-submission-explicit.svg) show separate experiment results.

All configurations reached four Handler slots. Start with one partition when work can share batches; add partitions only when measured key locality offsets fragmentation. Routing equal keys does not serialize separate batches or guarantee all copies enter one batch. These finite waves are not saturation limits or universal partition guidance.
